0. 通用约定

0.1 鉴权方式

除 POST /api/auth/login 外，所有接口均需携带 JWT：

Authorization: Bearer <token>

登录成功返回 token；拦截器校验失败返回 {"code":401,"msg":"未登录或令牌已过期"}。

0.2 统一响应格式

{ "code": 200, "msg": "ok", "data": { } }
code含义
200成功（data 为业务数据）
400参数校验失败
401未登录 / 令牌失效
403权限不足
500服务器异常

0.3 分页参数

列表接口统一支持 page（默认 1）与 size（默认 10）查询参数，返回 MyBatis-Plus 分页结构：

{ "records": [...], "total": 22, "size": 10, "current": 1 }

10. 文件上传（/api/upload）

10.1 通用图片上传

POST /api/upload　登录

multipart/form-data：字段名 file（单文件）。

响应 data：{ fileName, url } —— fileName 是用户原始文件名（只用于回显），url 形如 /uploads/<32位UUID>.<扩展名>，可直接当图片地址用。

两道校验（2026-10-04 加），任一不过就 code=400 且文件不落盘：

顺序校验通过条件不通过时的 msg
①扩展名白名单文件名最后一个点之后的部分（转小写）属于 jpg / jpeg / png / gif / webp / bmp只允许上传图片（jpg / jpeg / png / gif / webp / bmp）
②文件头（magic bytes）前 12 字节与该扩展名对应的图片格式一致（JPEG FF D8 FF、PNG 89 50 4E 47、GIF GIF8、BMP BM、WEBP RIFF....WEBP）文件内容不是有效图片
为什么两道都要：只做 ①，把 evil.html 改名成 evil.jpg 就绕过（后缀是客户端随便写的）；只做 ② 也不够 —— 文件名带 .html 的图片会被当网页返回，浏览器按 Content-Type 解释就执行了。

落盘文件名只由「UUID + 白名单后缀」拼成，不含任何用户输入，所以路径一定在上传目录内。

上传后由 GET /uploads/xxx.jpg 直接读磁盘返回（WebConfig 静态资源映射，不需要带 token）。

前端调用点：用户端 MyPlants.vue（植物照片、生长记录照片）、AddPlantWizard.vue、ExecutionDialog.vue（现场照片，走 el-upload 原生 XHR）；管理端 Species.vue、Disease.vue、ExecutionDialog.vue。各调用点都有一份与后端一致的后缀白名单做前置提示（真正的防线仍在后端）。

13.1 对话

参数类型必填说明

响应 data：

字段类型说明

toolsUsedString[]本轮真实执行过的工具名。⚠️ 前端默认不显示（函数名属内部实现，不该摊给终端用户）；地址栏加 ?agentDebug=1 才在气泡下方渲染成「调用了：xxx」。接口本身照常返回，不受该开关影响
degradedbooleantrue = 走了降级（模型不可用，回复来自预置答案或固定话术）。前端据此显示「离线模式」角标
guardString读数闸门（ReadingGuard）对本轮的判定：ok = 调过工具；no-tool = 没调工具但也没报读数（打招呼、如实说"查不到"、复述上下文里已有的数字）；hit = 没调工具却报了一个上下文里找不到出处的读数；replaced = 命中且重试仍在编，回答已被替换成代码直接查库的读数（2026-09-30 深夜加的第 5 态）；skip = 闸门没参与（离线降级）。⚠️ 当前配置为 on：命中后重试一次；重试仍命中且回答指向该用户名下的植物 → 换成实查读数（replaced），其余情况原样返回。界面上同样只在 ?agentDebug=1 时显示成一橙色诊断行
⚠️ degraded 必须一路传到界面显示，不许隐藏 —— 用缓存冒充实时结果是欺骗。
读数闸门为什么存在（演示会问）：大模型可能这一轮压根没查库，直接报一个看起来很像的读数
（2026-09-30 实测：助手答「土壤湿度 32%」，同一时刻盆栽卡片是 0.0%，而 32 这个数全库都不存在）。
「调没调工具」是模型的概率选择，prompt 只能压低概率、压不到零，所以在代码里设一道它绕不过去的闸。
判据 = 没调工具 且 回答里的读数在本次上下文里找不到出处（复述不算编造）。
开关 farm.agent.guard：off（完全不判定）/ dry-run（只记录，回答不动）/ on（命中后重试一次；
重试仍命中且回答指向该用户名下真实存在的植物 → 换成代码实查的读数（replaced）；
其余情况原样返回 —— 判据会误伤"通用养护常识"类提问，一刀切替换就是把一条正确回答换成"我查不到"）。
📌 2026-09-30 定档 on，不是拍脑袋：18 轮普查 hit=0/18（正常问法一次都没被打扰）。
🔴 值必须带引号写 "on"：YAML 1.1 会把裸 on 解析成布尔 true，注入 String 就成了 "true"，闸门静默退化成 dry-run ——
2026-09-30 深夜就是这么踩的（用户反馈助手又编了个 32%，复现时发现那一问只花了一次模型调用的时间 = 没发生重试），修法与证据见 实测记录 十.135。
⚠️ "演示当天不会被触发"这句话已被实测推翻：那条 32% 就出在「我茉莉现在的土壤湿度是多少？」上，连续两次判 hit。取值仍以 application.yml 为准。

②模型不可用 且 命中预置答案（离线预置回答）…，degraded=true
③模型不可用 且 未命中「智能助手暂时不可用，请稍后再试。系统其它功能不受影响。」，degraded=true

预置答案（8 条，agent-fallback.json）只放与用户数据无关的通用问答（"你能做什么""怎么添加植物"）。
带盆栽数值、位置、编号的答案一律不进缓存 —— 否则模型挂掉时会端出一个看着像实时、其实已经过期的数字。

13.2 探活

GET /api/agent/status → data: "ok"。前端可用它判断助手是否可用。

17. 种植物养护计划（/api/plants/{id}/care-plan）🆕 2026-10-02

为什么单独列一节：本文件的 §1~§13 是 2026-08-10 的接口分组，/api/plants 这一组当时就没写全（见文末勘误）。
本节只补 2026-10-02 新增的这一个接口，其余接口以 为准。

作用：把品种档案里的「浇水周期 / 施肥周期」变成这株植物自己的农事任务（type=custom），直接落进首页「今日农事清单」。

项内容
方法 / 路径POST /api/plants/{id}/care-plan
鉴权需登录（Authorization: Bearer <token>）；管理员可为任意植物生成，普通用户只能为自己名下的生成，否则 403
请求体无
响应{code, msg, data:{plant, created, skipped, items:[{title, cycleDays, repeatType, intervalDays, remindTime}]}}
副作用reminder 表新增 0~2 行（source='养护计划'、plant_id=该植物）；同名待办已存在则跳过
周期换算2026-10-04 起：≤1 天→daily，其余→interval（每 N 天），N 落进 reminder.interval_days（改版前是就近映射成 weekly/monthly，真实间隔会被拉成 7/30 天）；remind_time 兼作锚点，今天该做 ⟺ (今天 − 锚点日期) 天数 % N == 0
前端调用方用户端「我的种植」→ 详情抽屉里的「🪴 生成养护计划」按钮

示例响应（薄荷：浇水 2 天 / 施肥 20 天，2026-10-04 实测）：

{ "code": 200, "msg": "success",
  "data": { "plant": "薄荷", "created": 2, "skipped": 0,
    "items": [ { "title": "💧 浇水", "cycleDays": 2,  "repeatType": "interval", "intervalDays": 2,  "remindTime": "2026-10-04 14:00" },
               { "title": "🌿 施肥", "cycleDays": 20, "repeatType": "interval", "intervalDays": 20, "remindTime": "2026-10-04 14:00" } ] } }

落库后的两条任务（source 为「养护计划」）：repeat_type 是 interval、interval_days 是 2 和 20、remind_time 既是首次提醒时刻也是锚点 ⇒ 生成当天就进「今日农事清单」，之后每 2 天 / 每 20 天再回来。

再点一次的响应：{"created": 0, "skipped": 2, "items": []} —— 去重生效，不会堆重复任务。

详细实现与实测数据见 的 CarePlanService.java 一节。
