## 0. 通用约定

### 0.1 鉴权方式

除 `POST /api/auth/login` 外，所有接口均需携带 JWT：

```
Authorization: Bearer <token>
```

登录成功返回 token；拦截器校验失败返回 `{"code":401,"msg":"未登录或令牌已过期"}`。

### 0.2 统一响应格式

```json
{ "code": 200, "msg": "ok", "data": { } }
```

| code | 含义 |
|------|------|
| 200  | 成功（data 为业务数据） |
| 400  | 参数校验失败 |
| 401  | 未登录 / 令牌失效 |
| 403  | 权限不足 |
| 500  | 服务器异常 |

### 0.3 分页参数

列表接口统一支持 `page`（默认 1）与 `size`（默认 10）查询参数，返回 MyBatis-Plus 分页结构：

```json
{ "records": [...], "total": 22, "size": 10, "current": 1 }
```

### 0.4 四类角色（RBAC）

| role_id | role_code | 说明 |
|---------|-----------|------|
| 1 | ADMIN | 超级管理员：账号管理、操作日志、数据备份、天气刷新 |
| 2 | FARM_ADMIN | 农场管理员：全部业务功能 |
| 3 | AGRONOMIST | 农技人员：提醒管理、记录与统计 |
| 4 | WORKER | 普通作业人员：我的任务、填报记录、上传图片 |

## 1. 认证与账号（/api/auth）

### 1.1 登录

`POST /api/auth/login`　公开接口

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| username | String | ✅ | 账号 |

`GET /api/auth/me`　登录

### 2.1 任务分页查询

`GET /api/tasks`　登录

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| status | String | 否 | pending/doing/completed/overdue/exception |
| taskType | String | 否 | 整地/播种/施肥/灌溉/打药/除草/采收 |
| landId | Long | 否 | 地块筛选 |
| assigneeId | Long | 否 | 执行人筛选 |

每条记录动态附加：`landName / assignerName / assigneeName / isOverdue`（isOverdue=截止时间已过且未完成）。

### 2.2 我的任务

`GET /api/tasks/mine`　普通作业人员

仅返回当前登录执行人的任务，`data` 同上。

### 2.3 任务详情

`GET /api/tasks/{id}`　登录

响应 `data`：`{ task, inputs: [农资投入], attachments: [现场图片] }`

### 2.4 派发任务

`POST /api/tasks`　农场管理员/农技人员/超管

请求体：`{ title, taskType, landId, content, assigneeId, deadline }`，taskNo 自动生成（`RW-yyyyMMddHHmmss`），创建后 WebSocket 通知执行人。

### 2.5 任务状态流转

`PUT /api/tasks/{id}/status?status=doing|completed|exception`　执行人/派发人

状态机：`pending → doing → completed / exception`；任务完成后自动记录 complete_time，并通知派发人。

### 2.6 任务填报

`PUT /api/tasks/{id}/report`　执行人

请求体：

```json
{
  "summary": "操作摘要",
  "workHours": 2.5,
  "inputs": [
    { "inputType": "fertilizer", "name": "尿素", "amount": 50, "unit": "kg", "dilution": null, "remark": "全田撒施" }
  ]
}
```

`inputType` 取值：seed（种子）/ fertilizer（肥料）/ pesticide（农药）/ water（水）。填报后自动标记任务完成并通知派发人。

### 2.7 上传现场图片

`POST /api/tasks/{id}/attachment`　执行人/派发人

`multipart/form-data`：字段名 `file`。文件以 UUID 命名存储于 `upload-dir`，数据库记录 fileName/filePath/uploadTime，静态访问路径 `/uploads/<文件名>`。

### 2.8 删除任务

`DELETE /api/tasks/{id}`　派发人/超管

## 5. 数据统计（/api/stats）

### 5.1 看板总览

`GET /api/stats/overview`　登录

响应 `data`：

```json
{
  "total": 22,
  "statusDist": { "pending": 6, "doing": 2, "completed": 11, "overdue": 1, "exception": 2 },
  "typeDist":  { "整地": 1, "打药": 4, ... },
  "people":    { "张师傅": { "total": 15, "done": 7, "onTimeRate": 100 } },
  "landDist":  { "1": 8, "2": 2 }
}
```

说明：overdue 为动态口径（pending/doing 且截止时间已过）；people 按时完成率 = 完成时间 ≤ 截止时间的已完成任务占比。

### 5.2 提醒处理闭环统计

`GET /api/stats/reminders`　登录（管理角色使用）

响应 `data`：

```json
{
  "total": 12, "pending": 5, "done": 7, "cancelled": 0, "rate": 58.3,
  "byType": { "growth": { "total": 3, "done": 2 }, "solar": { "total": 2, "done": 1 } }
}
```

说明：rate = 已完成数 / 总数 × 100（保留 1 位小数）；byType 按提醒来源（growth/solar/weather/custom）分组，只含非空类型。配合前端"确认完成"按钮形成提醒处理闭环。

## 10. 文件上传（/api/upload）

### 10.1 通用图片上传

`POST /api/upload`　登录

`multipart/form-data`：字段名 `file`（单文件）。

响应 `data`：`{ fileName, url }` —— `fileName` 是用户原始文件名（只用于回显），`url` 形如 `/uploads/<32位UUID>.<扩展名>`，可直接当图片地址用。

**两道校验（2026-10-04 加）**，任一不过就 `code=400` 且**文件不落盘**：

| 顺序 | 校验 | 通过条件 | 不通过时的 `msg` |
|---|---|---|---|
| ① | **扩展名白名单** | 文件名最后一个点之后的部分（转小写）属于 `jpg / jpeg / png / gif / webp / bmp` | `只允许上传图片（jpg / jpeg / png / gif / webp / bmp）` |
| ② | **文件头（magic bytes）** | 前 12 字节与该扩展名对应的图片格式一致（JPEG `FF D8 FF`、PNG `89 50 4E 47`、GIF `GIF8`、BMP `BM`、WEBP `RIFF....WEBP`） | `文件内容不是有效图片` |

> 为什么两道都要：只做 ①，把 `evil.html` 改名成 `evil.jpg` 就绕过（后缀是客户端随便写的）；只做 ② 也不够 —— 文件名带 `.html` 的图片会被当网页返回，浏览器按 `Content-Type` 解释就执行了。
>
> 落盘文件名只由「UUID + 白名单后缀」拼成，**不含任何用户输入**，所以路径一定在上传目录内。
>
> 上传后由 `GET /uploads/xxx.jpg` 直接读磁盘返回（`WebConfig` 静态资源映射，**不需要带 token**）。

**前端调用点**：用户端 `MyPlants.vue`（植物照片、生长记录照片）、`AddPlantWizard.vue`、`ExecutionDialog.vue`（现场照片，走 el-upload 原生 XHR）；管理端 `Species.vue`、`Disease.vue`、`ExecutionDialog.vue`。各调用点都有一份与后端一致的后缀白名单做前置提示（真正的防线仍在后端）。

## 13. 智能助手（/api/agent）

> 2026-09 新增模块（详见 `docs/Agent模块设计方案.md`、`docs/Agent模块实施计划.md`）。
> 可用 `farm.agent.enabled` 一键关闭；**关闭时本节所有路径返回 `code=500`** —— 这是本项目全局异常处理的既有约定，不是 404。

### 13.1 对话

`POST /api/agent/chat`

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| conversationId | String | ❌ | 会话 id。**同一 id 的多次请求共享上下文**（多轮对话的来源）；不传则落到 `default` 会话 |
| message | String | ✅ | 用户问题（中文，支持口语化） |

响应 `data`：

| 字段 | 类型 | 说明 |
|------|------|------|
| reply | String | 助手回复 |
| toolsUsed | String[] | 本轮**真实执行**过的工具名。⚠️ 前端**默认不显示**（函数名属内部实现，不该摊给终端用户）；地址栏加 `?agentDebug=1` 才在气泡下方渲染成「调用了：xxx」。接口本身照常返回，不受该开关影响 |
| degraded | boolean | **true = 走了降级**（模型不可用，回复来自预置答案或固定话术）。前端据此显示「离线模式」角标 |
| guard | String | **读数闸门**（`ReadingGuard`）对本轮的判定：`ok` = 调过工具；`no-tool` = 没调工具但也没报读数（打招呼、如实说"查不到"、复述上下文里已有的数字）；`hit` = 没调工具却报了一个上下文里找不到出处的读数；`replaced` = 命中且重试仍在编，**回答已被替换成代码直接查库的读数**（2026-09-30 深夜加的第 5 态）；`skip` = 闸门没参与（离线降级）。⚠️ **当前配置为 `on`：命中后重试一次；重试仍命中且回答指向该用户名下的植物 → 换成实查读数（`replaced`），其余情况原样返回**。界面上同样只在 `?agentDebug=1` 时显示成一橙色诊断行 |

> ⚠️ `degraded` 必须一路传到界面显示，不许隐藏 —— 用缓存冒充实时结果是欺骗。

> **读数闸门为什么存在**（演示会问）：大模型可能**这一轮压根没查库**，直接报一个看起来很像的读数
> （2026-09-30 实测：助手答「土壤湿度 32%」，同一时刻盆栽卡片是 0.0%，而 32 这个数全库都不存在）。
> 「调没调工具」是模型的概率选择，**prompt 只能压低概率、压不到零**，所以在代码里设一道它绕不过去的闸。
> 判据 = 没调工具 **且** 回答里的读数在本次上下文里找不到出处（复述不算编造）。
> 开关 `farm.agent.guard`：`off`（完全不判定）/ `dry-run`（只记录，回答不动）/ `on`（命中后**重试一次**；
> 重试仍命中且回答指向**该用户名下真实存在的植物** → 换成代码实查的读数（`replaced`）；
> 其余情况原样返回 —— 判据会误伤"通用养护常识"类提问，一刀切替换就是把一条正确回答换成"我查不到"）。
> 📌 **2026-09-30 定档 `on`**，不是拍脑袋：18 轮普查 `hit=0/18`（正常问法一次都没被打扰）。
> 🔴 **值必须带引号写 `"on"`**：YAML 1.1 会把裸 `on` 解析成布尔 `true`，注入 String 就成了 `"true"`，闸门**静默退化成 dry-run** ——
> 2026-09-30 深夜就是这么踩的（用户反馈助手又编了个 32%，复现时发现那一问只花了一次模型调用的时间 = 没发生重试）。
> ⚠️ **"演示当天不会被触发"这句话已被实测推翻**：那条 32% 就出在「我茉莉现在的土壤湿度是多少？」上，**连续两次**判 `hit`。取值仍以 `application.yml` 为准。

**工具清单（6 个）**：

| 工具 | 类型 | 作用 |
|------|------|------|
| getSensorReading | 只读 | 查某盆植物的最新环境读数 + 品种适宜区间 + 是否达标判定 |
| getPlantProfile | 只读 | 查品种资料与当前生长阶段（浇水/施肥周期、适宜温湿度、光照、养护要点）。**不限于用户名下的植物**：品种库里有的品种（188 个，如草莓）也照给，但返回里会写明"不属于该用户"（2026-09-30 深夜补，十.136）|
| getSusceptibleDiseases | 只读 | 反查「某盆植物易感哪些病虫害」：遍历 `plant_disease` 逐条比对登记的易感植物，命中即收录；未收录如实说明 |
| getWeather | 只读 | 查未来三天天气（南宁/柳州/桂林） |
| searchKnowledge | 只读 | **RAG 语义检索**知识库（病虫害 158 条 + 节气 24 条 = 182 条向量） |
| createFarmTask | **写** | 建农事任务。归属校验与人工建任务走同一套业务方法 |

> **为什么 `getSusceptibleDiseases` 是确定性反查、不走 RAG**：`plant_disease` 表的方向是
> **「每条病 → 哪些植物易感」**，而用户问的是反方向**「这盆植物 → 哪些病」**。
> 拿反向的问句去喂语义检索，命中哪几条纯看运气 —— 实测同一句话两次答案互相矛盾：
> 一次**漏报**（库里登记的植物被答成"不在名单里"），一次**编出不存在的病名**
> （答出「蛞蝓」「蚧壳虫」，而库里对不上）。这类"答案取决于结构化字段比对"的判断
> 在代码里算准再给模型，与本平台既有的节气换算同一个思路。

**三级降级**（2026-09-29 演练实测：第③级 390ms 返回、第②级 68ms）：

| 级 | 触发条件 | 返回 |
|---|---------|------|
| ① | 正常 | 模型回答 |
| ② | 模型不可用 **且** 命中预置答案 | `（离线预置回答）…`，`degraded=true` |
| ③ | 模型不可用 **且** 未命中 | 「智能助手暂时不可用，请稍后再试。系统其它功能不受影响。」，`degraded=true` |

预置答案（8 条，`agent-fallback.json`）**只放与用户数据无关的通用问答**（"你能做什么""怎么添加植物"）。
带盆栽数值、位置、编号的答案**一律不进缓存** —— 否则模型挂掉时会端出一个看着像实时、其实已经过期的数字。

## 15. 定时任务一览

| 任务（所在类） | 周期 | 说明 |
|------|------|------|
| `ReminderService` | 每日 00:05 | 把「重复类型且已完成」的任务重置回待办（`cron = "0 5 0 * * *"`） |
| `WeatherWarnScheduler` | 每 2 小时 | 拉取配置城市列表的天气预报 → 规则匹配生成天气预警提醒 + 定向推送 |
| `PlantAdviceEngine` | 每 5 分钟 | 全量扫盆栽 → 适宜度/病虫害/明日有雨/恢复四路检查，生成种植建议 |
| `OfflineCheckScheduler` | 每 15 秒 | 超过在线窗口未上报的设备统一置离线（LWT 之外的兜底） |
| `BackupScheduler` | 每日 03:00 | mysqldump 全量备份，保留 7 天（`cron = "0 0 3 * * ?"`） |
| `SensorDataCleanScheduler` | 每日 03:30 | 删除 30 天前的 `sensor_data`（`cron = "0 30 3 * * ?"`） |
| `SimulatorService` | 每 60 秒 | 演示用模拟数据生成（`farm.simulator.enabled=false` 时直接 return，当前即关闭态） |
| `ReminderExpiryScheduler` | 每 5 分钟 | 删除「下发日期已经过去」的未处理 `plant_advice` / `plant_pest`（TTL=1 天，物理删除），让引擎按新日期重新生成；**不动** `custom` / `sensor` / `weather` |
| `TaskDueNotifyScheduler` | 每 60 秒 | **农事任务到点推送**（2026-10-02 新增）：把用户自建的 `custom` 任务按重复规则折算成「今天该做的那一次」，到点推 `deadline` 通知给本人；同一条任务当天只推一次，迟到超 10 分钟不补推 |

> **以上为 2026-10-02 复测的 9 个 `@Scheduled`**（`@EnableScheduling` 在 `FarmPlatformApplication`）。
> 原表三行（`TaskDeadlineScheduler` / `WeatherWarnScheduler` / `BackupScheduler`）里的 **`TaskDeadlineScheduler` 已不存在**，
> 但它当年承诺的「任务到期推送」**已于 2026-10-02 真正实现** —— 由 `TaskDueNotifyScheduler` 承担（见上一行）。
> 在此之前，任务到期只靠前端打开页面时加载 + 每 60 秒轮询呈现（现在**两层都有**：页面轮询 + 后端到点推送）。

## 17. 种植物养护计划（/api/plants/{id}/care-plan）🆕 2026-10-02

> **为什么单独列一节**：本文件的 §1~§13 是 2026-08-10 的接口分组，`/api/plants` 这一组当时就没写全（见文末勘误）。
> 本节只补 2026-10-02 新增的这一个接口 为准。

**作用**：把品种档案里的「浇水周期 / 施肥周期」变成这株植物自己的农事任务（`type=custom`），直接落进首页「今日农事清单」。

| 项 | 内容 |
|---|---|
| 方法 / 路径 | `POST /api/plants/{id}/care-plan` |
| 鉴权 | 需登录（`Authorization: Bearer <token>`）；管理员可为任意植物生成，普通用户只能为自己名下的生成，否则 403 |
| 请求体 | 无 |
| 响应 | `{code, msg, data:{plant, created, skipped, items:[{title, cycleDays, repeatType, intervalDays, remindTime}]}}` |
| 副作用 | `reminder` 表新增 0~2 行（`source='养护计划'`、`plant_id=该植物`）；同名待办已存在则跳过 |
| 周期换算 | **2026-10-04 起**：≤1 天→`daily`，**其余→`interval`（每 N 天）**，N 落进 `reminder.interval_days`（改版前是就近映射成 weekly/monthly，真实间隔会被拉成 7/30 天）；`remind_time` 兼作锚点，今天该做 ⟺ (今天 − 锚点日期) 天数 % N == 0 |
| 前端调用方 | 用户端「我的种植」→ 详情抽屉里的「🪴 生成养护计划」按钮 |

**示例响应**（薄荷：浇水 2 天 / 施肥 20 天，2026-10-04 实测）：

```json
{ "code": 200, "msg": "success",
  "data": { "plant": "薄荷", "created": 2, "skipped": 0,
    "items": [ { "title": "💧 浇水", "cycleDays": 2,  "repeatType": "interval", "intervalDays": 2,  "remindTime": "2026-10-04 14:00" },
               { "title": "🌿 施肥", "cycleDays": 20, "repeatType": "interval", "intervalDays": 20, "remindTime": "2026-10-04 14:00" } ] } }
```

**落库后的两条任务**（`source` 为「养护计划」）：`repeat_type` 是 `interval`、`interval_days` 是 2 和 20、`remind_time` 既是首次提醒时刻也是锚点 ⇒ 生成当天就进「今日农事清单」，之后每 2 天 / 每 20 天再回来。

**再点一次的响应**：`{"created": 0, "skipped": 2, "items": []}` —— 去重生效，不会堆重复任务。

> 详细实现与实测数据 的 `CarePlanService.java` 一节。
